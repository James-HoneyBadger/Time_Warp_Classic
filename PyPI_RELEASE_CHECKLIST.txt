# Time Warp Classic - Release Runbook

How a release actually ships today, plus the status of the 1.6.0 release.

---

## How a release ships

Releases are tag-driven. Pushing a tag is the only manual step.

| Tag | Effect |
|-----|--------|
| `vX.Y.Z` | PyPI publish workflow + both container workflows |
| `vX.Y.Z-rcN`, `-betaN`, `-alphaN` | TestPyPI publish workflow only |

Workflows involved:

- `.github/workflows/publish-pypi.yml` - build, `twine check --strict`, publish
  to PyPI through OIDC Trusted Publishing (no API token stored).
- `.github/workflows/publish-testpypi.yml` - the same, for prerelease tags.
- `.github/workflows/publish-ghcr.yml` - desktop IDE image.
- `.github/workflows/publish-ghcr-web.yml` - web IDE image.

```bash
git tag -a vX.Y.Z -m "Time Warp Classic X.Y.Z"
git push origin vX.Y.Z
```

Both container workflows also accept a manual `workflow_dispatch` run with a
`tag` input, so an already published release can be rebuilt without a new
version:

```bash
gh workflow run publish-ghcr-web.yml --ref main -f tag=v1.6.0
```

## What the 1.6.0 release published

| Artefact | Location | Notes |
|----------|----------|-------|
| Wheel | `timewarp_classic-1.6.0-py3-none-any.whl` | ~254 KB, 68 files |
| Source distribution | `timewarp_classic-1.6.0.tar.gz` | ~349 KB |
| PyPI project | https://pypi.org/project/timewarp-classic/ | versions 1.3.0, 1.3.4, 1.5.0, 1.6.0 |
| GitHub release | `v1.6.0` | marked Latest, body from `CHANGELOG.md` |
| Desktop image | `ghcr.io/james-honeybadger/time-warp-classic` | linux/amd64 + linux/arm64 |
| Web image | `ghcr.io/james-honeybadger/time-warp-classic-web` | linux/amd64 + linux/arm64 |

Image tags per release: `latest`, `X.Y`, `X.Y.Z` and `vX.Y.Z`. `latest` is
skipped for prerelease tags.

Both images now carry the same tag set: `publish-ghcr-web.yml` gained the
`type=ref,event=tag` rule during 1.6.0, and the missing `v1.6.0` alias on the
web image was added afterwards with the manual rebuild below.

The 1.5.0 desktop image was first published amd64-only and rebuilt for both
architectures afterwards; releases from 1.6.0 on are multi-arch first time.

## Verifying a published release

```bash
# PyPI metadata (the JSON endpoint is CDN cached, /simple/ is not)
curl -s https://pypi.org/simple/timewarp-classic/ | grep -o 'timewarp_classic-[0-9.]*tar.gz' | tail -3

# Install the released package in a throwaway environment
python3 -m venv /tmp/pypicheck
/tmp/pypicheck/bin/pip install -q --upgrade pip
/tmp/pypicheck/bin/pip install -q timewarp-classic==1.6.0
/tmp/pypicheck/bin/timewarp --version

# Containers
docker pull ghcr.io/james-honeybadger/time-warp-classic:1.6.0
docker pull ghcr.io/james-honeybadger/time-warp-classic-web:1.6.0
docker run -d --rm -p 8000:8000 ghcr.io/james-honeybadger/time-warp-classic-web:1.6.0
curl -s http://localhost:8000/healthz

# Workflow results
gh run list --limit 6
```

## Checklist for the next release

1. `./venv/bin/python -m pytest tests -q -p no:cacheprovider` - full suite green.
2. Bump the version everywhere it appears:
   - `pyproject.toml`
   - `core/__init__.py` (`__version__`)
   - `core/optimizations/__init__.py` (`__version__`)
   - `gui/dialogs.py` (About dialog)
   - `README.md` (version badge)
   - `docs/INDEX.md`
3. Add a `CHANGELOG.md` section; its text becomes the GitHub release body.
4. Rebuild and validate:
   ```bash
   rm -rf dist build
   ./venv/bin/python -m build
   ./venv/bin/twine check --strict dist/*
   ```
5. Confirm the wheel ships what users need and no bytecode:
   ```bash
   ./venv/bin/python -c "import zipfile,glob; \
     names=zipfile.ZipFile(glob.glob('dist/*.whl')[0]).namelist(); \
     print(len(names),'files'); \
     print(sum('__pycache__' in n or n.endswith('.pyc') for n in names),'bytecode entries')"
   ```
6. Commit and push `main`, then tag and push the tag.
7. Watch the workflows and verify with the commands above.
8. Create or update the GitHub release with the changelog section.

## Manual fallback (no CI)

`release_to_pypi.sh` still works when the workflows are unavailable:

```bash
bash release_to_pypi.sh testpypi   # upload to test.pypi.org first
bash release_to_pypi.sh pypi       # production upload
```

It cleans `dist/`, builds, validates and uploads with `twine`. It needs a PyPI
API token in `~/.pypirc` or `TWINE_PASSWORD`, so trusted publishing stays the
preferred path.

## Troubleshooting

- **`twine check` fails** - rerun with `--verbose`; usually a `README.md`
  rendering problem or an invalid classifier.
- **PyPI rejects the version** - published versions are immutable; bump the
  version instead of re-uploading.
- **`pip install` still shows the old version** - wait for the CDN, or query
  `https://pypi.org/simple/timewarp-classic/`.
- **Image pull fails with 403** - that tag has not been pushed yet, or the
  workflow failed; check `gh run list --workflow publish-ghcr-web.yml`.
- **Container exits immediately** - the web image needs no environment; the
  desktop image needs `DISPLAY` and an X11 socket.
